# ADR 0004 — 全局检索配置与入库限制

- 状态：已采纳（访谈第 4–5 轮）
- 日期：2026-09-05
- 前置：[0003](./0003-chunking-ui-tools.md)
- 取代：[0001](./0001-v1-product-decisions.md) 第 4 条（每库 embedding）；[0003](./0003-chunking-ui-tools.md) 固定 chunk / 建库选模型

## 决策

### 全局唯一 embedding 与分块 / 召回

- 所有知识库共用 **一个** embedding 模型，在全局配置，不在单库上选。
- `topK`、匹配度阈值、`chunkSize`、`chunkOverlap` 同样全局一致、全局可配。
- 默认值：`topK = 5`，匹配度阈值 `0.5`，`chunkSize = 1024`，`chunkOverlap = 200`；切分策略仍是 Markdown 结构切。
- 多库检索：每库向量检索先丢掉低于匹配度阈值的分块，再取 `topK`，按余弦分合成后截断到全局 `topK`（同一模型，分数可比）。不使用跨模型 RRF。
- 全部低于阈值：当次无相关资料，不报错、不注入。

### 配置放哪（Q28-A）

- 设置侧栏一级 **「知识库」**：选用全局 embedding 模型，编辑 `topK` / 匹配度阈值 / `chunkSize` / `chunkOverlap`。
- ChatApp 第四 Tab 只管建库、条目。未选 embedding 时 Tab 内横幅引导去设置。
- MinerU / open-mineru 在设置一级 **「文档处理」** 里选用其中一个并填凭证，与检索参数分开。所有知识库共用当前选中的处理器。

### 改参数如何重建（Q29-A）

- 改 embedding 或 `chunkSize` / `chunkOverlap`：先确认「将重建全部知识库索引」（写明会再次消耗 MinerU 与 embedding 配额）。确认后清空每个库的 sqlite-vec，条目保持文件/笔记副本并标 `pending` 再入队。进行中的任务标 `failed` 后重排。
- 改 `topK` 或匹配度阈值：立即用于下次检索，无确认、不重建。
- 未配置 embedding：禁止加入需要向量化的条目；检索返回明确错误并引导去设置。

### 文件类型与上限（Q23-A）

- 选择器只接受 `.txt` `.md` `.markdown` `.pdf` `.docx`；其它扩展名拒绝。
- 单文件 100MB；PDF 另受处理器限制（超时或对方拒收 → 该条失败）。
- 一次最多加入 20 个文件。笔记约 10 万字（已在 0003）。

### 文件名冲突（Q24-B）

- 同一库出现同名文件时弹出「保留两者 / 替换已有」。
- 保留两者：磁盘加后缀（`报告 (2).pdf`），两条都索引。
- 替换：删除旧条目的副本与索引，再加入新文件。

批量加入时一条对话框列出全部冲突，每行选「保留两者」或「替换」，底部可「全部保留 / 全部替换」，确认后一次执行（Q30-A）。

### 进度（Q25-A）

- 列表轮询：排队 / 处理中 / 已完成 / 失败。
- 失败行：短错误 + 「重新处理」。不假造进度条。处理中不可取消（停 = 等失败或删条目）。

### 来源引用（Q26-A）

- 点击展开当次注入片段（popover）。
- 「在知识库中查看」切到知识库 Tab 并选中对应条目。
- 不把全文再写入对话记录。

### 处理器运行（Q27-A）

- 设置 → 文档处理：下拉选用 `mineru` 或 `open-mineru`，再填对应凭证；「测试连接」。
- 未配置当前处理器时 PDF 入库失败，条目提示去设置 → 文档处理。不按库选择、不回退到另一种处理器。
- 全局同时只跑 1 个 PDF 处理器任务；同条目 embedding 批大小约 10。
- 单条处理超时 10 分钟 → `failed`。

## 后果

- 创建知识库不再选择 embedding 或处理器，只填名称。
- 换全局 embedding 或 chunk 参数会影响**每一个**已建库，不能再「只重建当前库」。
- 设置出现两个一级项：「知识库」（检索参数）与「文档处理」（处理器凭证）。
- 未配置全局 embedding 时，加入条目与检索都被拦截，并引导去设置 → 知识库。
